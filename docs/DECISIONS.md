# Решения

Короткие решения, принятые без остановки разработки.

1. **Стек.** Vite + React + TypeScript и Fastify + TypeScript в одном npm-workspace. Домен живёт в `@taskos/core` и тестируется без браузера и без Grok. Kubernetes, Redis и PostgreSQL не используются.

2. **Один Grok.** Builder и Reviewer — два отдельных процесса `grok` без `--resume`. Модель берётся из `.taskos/config.json` (`grok-4.7`). Разные вендоры не имитируются.

3. **Подпись режима.** `fast` → «Grok ×1», `verified` → «Grok ×2 review», `deep` → «Grok ×3 deep». Это число ролей, а не обещание другой модели. В `deep` исправлений не больше двух.

4. **Вес REVIEW в режиме fast.** Отдельный reviewer не запускается. Флаг `reviewSkipped` закрывает 15% шкалы. Иначе задача честно выполненного быстрого режима никогда не дошла бы до 100%.

5. **Вес TEST без кода.** Если `requiresCode = false`, тесты кода помечаются `skipped` и 15% засчитываются. Проверка такой задачи — это USER_QA.

6. **Исходный запрос.** Каноническая копия — `request.md`. Она пишется при создании и больше не открывается на запись. Заголовок и ТЗ могут уточняться отдельно.

7. **Мало данных.** Модель делает допущение и пишет его в spec. В `BLOCKED` задача уходит только если spec содержит `criticalQuestion`.

8. **Feedback.** Замечание сразу возвращает задачу в BUILD и снова запускает пайплайн. Отдельная кнопка «запусти ещё раз» не нужна.

9. **Коммит ветки задачи.** После успешного кодового прохода TaskOS делает обычный `git commit` на ветке `task/...`, если есть изменения кода. Каталоги `.taskos` и `.taskos-local` в этот коммит не входят и не считаются «грязным деревом»: иначе сама база задач блокировала бы переключение ветки. Их коммитит человек, когда хочет унести задачи на другой компьютер. В `main` коммит запрещён. Push и merge продукт не делает.

10. **Грязное дерево.** Ветку не переключаем и изменения пользователя не прячем. Показываем `REPO_DIRTY`.

11. **Секреты.** Если в индекс попали `.env`, ключи или `credentials.json`, коммит отменяется.

12. **Raw log.** Полный stdout/stderr остаётся в `.taskos-local` и не коммитится. Между компьютерами через git едет timeline и `runs/*.jsonl`.

13. **ETA.** Диапазон, не точная минута. Пока по этапу меньше трёх завершённых замеров, подпись начинается с «Оценка пока неточная». На USER_QA показывается «Ждёт вашей проверки».

14. **Качество по умолчанию.** `verified`: один builder и один независимый reviewer. Пользователь может выбрать fast или deep в форме.

15. **Код по умолчанию.** `requiresCodeMode = auto`. До spec это `false`. Spec может включить код. Явные «да» и «нет» в форме spec не перебивает.

16. **План.** Шаги хранятся в `task.json`. `plan.md` — читаемый снимок. Два JSON не синхронизируем вручную.

17. **Флаги CLI.** Используются только флаги, которые есть у установленного `grok` 1.0.46: `--prompt-file`, `--cwd`, `-m`, `--output-format`, `--json-schema`, `--permission-mode`, `--max-turns`, `--disallowed-tools`, `--deny`, `--rules`, `--no-subagents`. Флаг `--no-auto-update` из общей документации в `--help` этой сборки нет, поэтому он не передаётся.

18. **Разрешения headless.** Кодовый проход получает `bypassPermissions`, иначе CLI ждал бы человека в TTY. Опасный git закрыт `--deny`. Spec, plan, review и некодовый ответ идут в `--permission-mode plan` без shell.

19. **Заглушка AI.** `TASKOS_AI=fake` существует для тестов и локальной проверки пайплайна. В интерфейсе в этом режиме есть явная плашка. Запись задачи всё равно помечена провайдером `grok-build`: заглушка не выдаёт себя за другую модель.

20. **Порт.** Приложение слушает только `127.0.0.1`.

21. **Проект «автоматически».** Если в форме выбран авто-проект и spec вернул `projectName`, создаётся или находится проект с этим именем. «Без проекта» spec не переопределяет.

22. **Подтверждение.** «Подтвердить» переводит в `READY`. «Закрыть» переводит в `DONE` только из `READY`.

23. **Шрифты.** Интерфейс не тянет шрифты с Google. Локальный command center должен открываться без сети. Характер задают палитра, серифные заголовки системным Palatino/Georgia и моноширинная шкала прогресса.

24. **Цель задачи.** `task.goal` заполняется из ТЗ и показывается на обзоре. Старые `task.json` без поля читаются как `goal: null`. Версия схемы остаётся 1.

25. **Блокировка.** Lock создаётся через `open` с флагом `wx`, чтобы два запуска не прошли проверку одновременно. Мёртвый pid по-прежнему снимается.

26. **Пауза во время прогона.** Если на диске уже `PAUSED`, поздняя запись прогона не возвращает задачу в рабочий статус.

27. **Провалившееся ревью.** Задача всё равно доходит до `USER_QA`, если тесты не упали. Пользователь видит замечания и может отправить их обратно. Автоисправление остаётся только у режима `deep`, не больше двух циклов.

28. **Имя shell-инструмента.** В `grok` 1.0.46 для `--disallowed-tools` каноническое имя — `run_terminal_cmd`. В потоке `streaming-json` то же действие приходит как `run_terminal_command`. Timeline понимает оба.

29. **Запрет ухода в main.** Кодовый прогон дополнительно получает `--deny` на `checkout`/`switch` в `main` и `master` и на удаление веток. Это не заменяет проверку ветки перед коммитом TaskOS.

30. **Поле схемы.** У `grok` 1.0.46 `--output-format json` кладёт объект схемы в `structuredOutput`, не в `structured_output`. Оба имени читаются. Проверено локальным headless-запуском.
